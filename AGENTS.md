# AGENTS.md

## Что это за проект

**SourceCraftRepoHealthChecker** — веб-сервис оценки «здоровья» открытых репозиториев SourceCraft. Считает **Repo Health Score** (0–100) по шести категориям, объясняет оценку и формирует приоритизированные рекомендации. Авторизация — через **Я ID**.

Бэкенд реализуется на **C#** (луковичная архитектура) и **Go**. Обязательный стек ТЗ не задаёт — `C# + Go` это решение команды.

## Требования ТЗ (правила разработки)

### Источники данных

- Единственный источник — действующие **API и CLI SourceCraft**. Готовых выгрузок нет, сбор реализуем сами.
- Импорт репозиториев с внешних Git-платформ не требуется: анализируем только то, что размещено в SourceCraft.
- Security-оценка строится только на реальных результатах **AppSec SourceCraft** (SAST, SCA, secret scanning). Имитация собственного security-сканирования запрещена.
- Исходный код не хранить дольше и в большем объёме, чем нужно для анализа.
- Данные закрытого репозитория обрабатываются только в рамках прав авторизованного пользователя.

### Repo Health Score

- Шкала **0–100**, детализация по категориям, воспроизводимость и объяснимость, опора на факты.
- Шесть основных категорий (ориентировочные веса): Security 20%, Code health 20%, Активность 15%, Документация и лучшие практики 15%, CI/CD 15%, Issues 15%.
- Веса можно менять, но каждое исключение, объединение или изменение веса нужно явно обосновать и компенсировать другой метрикой.
- Отсутствие данных — отдельный статус **«Нет данных»**, а не автоматически плохой результат.
- Методика должна быть устойчива к перекосам: второстепенные показатели не доминируют, популярность не подменяет здоровье проекта, простые способы искусственно поднять Score не дают существенного эффекта.

### Рекомендации

Для каждой рекомендации указывать: обнаруженную проблему, почему она важна, подтверждающие факты, рекомендуемое действие, приоритет, ожидаемое влияние на Score. По возможности ссылаться на файл, pipeline, vulnerability, commit, issue или merge request.

### Обязательные пользовательские сценарии

- Публичный рейтинг открытых репозиториев: место, проект, ссылка, Score, лайки, язык, последняя активность; фильтр по языку; сортировка по Score, лайкам и активности; переход на страницу анализа.
- Страница анализа: итоговый Score, оценки по категориям, сильные и слабые стороны, объяснение расчёта, рекомендации, «Нет данных», дата последнего анализа.
- Авторизация через **Я ID** → выбор доступного репозитория → анализ собственного репозитория.
- Выгрузка отчёта минимум в одном формате: **Markdown или PDF**.

### Периодический анализ и масштаб

- Регулярный пересчёт по расписанию: повторный сбор данных, пересчёт Score, фиксация статуса и времени последнего анализа.
- Устойчивость к временной недоступности отдельных источников данных.
- Архитектура рассчитана на рост числа и объёма репозиториев; предусмотреть обоснованное масштабирование.
- Крупный репозиторий: **≥ 10 000** отслеживаемых файлов, **или ≥ 20 000** коммитов, **или ≥ 500 МБ** рабочей копии.

### Часть со звёздочкой

Опциональные направления: расширенный рейтинг, история и сравнение проектов; углублённая аналитика (review, issues, bus factor, карта владельцев); публичный API и quality badges; AI-summary и AI-рекомендации; защита публичного рейтинга от накрутки. Бонусные функции не компенсируют отсутствие обязательной части.

## Луковичная архитектура (C#)

Зависимости направлены строго внутрь, к `Domain`.

| Проект | Ответственность | Зависит от |
|--------|-----------------|------------|
| `SourceCraftRepoHealthChecker.Domain` | Ядро: сущности (`Entities/`), value-объекты, доменные правила. Не зависит ни от чего. | — |
| `SourceCraftRepoHealthChecker.Application` | Сценарии использования и абстракции (порты). | `Domain` |
| `SourceCraftRepoHealthChecker.infrastructure` | Адаптеры: EF Core/`DbContext`, внешние API, файлы. | `Application`, `Domain` |
| `SourceCraftRepoHealthChecker.Presenter` | Точка входа: веб-API, маппинг запросов, DI (composition root). | `Application`, `infrastructure` |

Правила:

- `Domain` не знает о БД, фреймворках и внешних сервисах.
- `Application` зависит только от `Domain` и собственных абстракций, не от `infrastructure`.
- `infrastructure` реализует абстракции `Application`; зависимости `infrastructure → Application → Domain` допустимы, обратные — нет.
- `Presenter` — composition root: единственный, кто ссылается и на `Application`, и на `infrastructure`, чтобы собрать DI-граф. Наружу от `Presenter` зависимостей нет.

## Методика Repo Health Score (ядро)

Расчёт живёт в `Application/HealthCheck` и настраивается через `IOptions<HealthCheckOptions>` (значения — в `Presenter/appsettings.json`), без хардкода чисел.

- **Общий Score (0–100):** взвешенное среднее оценок категорий. Категории со статусом **«Нет данных»** исключаются, веса доступных нормируются (отсутствие данных не ухудшает Score).
- **Оценка категории:** взвешенное среднее нормализованных метрик (`MetricScore.NormalizedScore`) — так объяснение воспроизводимо: метрики сходятся с баллом категории.
- **Нормализация метрики:** линейная от «худшего» к «лучшему» значению в границах шкалы из `ScoreScaleOptions`.
- **Веса категорий:** Security 20%, Code health 20%, Activity 15%, Documentation 15%, CI/CD 15%, Issues 15% (`CategoryWeightsOptions`).
- **Security:** метрики по критичности (Critical/High/Medium/Low), вес метрики = соответствующий штраф; исправленные находки — информационная метрика с весом 0.
- **Code health:** метрики TODO/FIXME/старые комментарии, вес метрики = штраф.
- **Активность/Issues:** дата последней активности, коммиты в окне, contributors, релизы (MR — по `MergeRequestsForFullScore`); зависшие issue считаются по `UpdatedAt` (с откатом на `CreatedAt`).
- **«Нет данных»** — отдельный статус, не плохой результат. Если Security недоступен (AppSec недоступен или не настроен), ядро добавляет явную пометку «Подключите AppSec SourceCraft» без штрафа.
- **Рекомендации** строятся на фактах из `MetricScore.RawValue` (например, «TODO — 47, самый старый комментарий — 200 дн.»), с приоритетом и `SourceReference`.
